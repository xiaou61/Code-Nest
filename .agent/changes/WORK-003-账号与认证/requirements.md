# 账号与认证需求

## 已确认事实

### 后端认证骨架（读源码确认）

- `AuthPort` 只有两个方法：`issue(String subject)` 与 `authenticate(String token)`；`Subject` 记录**只有 `id`，没有角色**。
- `AuthController` 的 `POST /api/v1/auth/token` **不校验任何凭据**，可为任意主体签发令牌；标了 `@Profile({"dev", "local"})`，注释自己写着"引入真实登录之前，绝不能让它出现在任何面向他人的环境里"。
- `MeController` 的 `GET /api/v1/me` 只返回 `subject`。
- `SecurityConfiguration`：`STATELESS`、关闭 CSRF、放行 `/actuator/health`、`/error` 与那个 dev 签发端点，**其余 `anyRequest().authenticated()`**；资源服务器复用同一个 `JwtDecoder`。
- `AuthProperties`：`secret` / `issuer` / `tokenTtl`（默认 2 小时）；未配置 `secret` 时生成一次性随机密钥并告警（重启即令牌全失效）；本地配置**已配** secret。
- `JwtAuthService` 签发的 claims 只有 `iss`、`sub`、`iat`、`exp`——**没有角色**。

### 数据与依赖现状

- **Flyway 迁移目录里只有一个 `.gitkeep`**：项目至今没有任何业务表。`users` 会是第一张。
- 测试数据的既有做法是把夹具放在 `classpath:db/testdata`（见 `paideia-persistence` 的 `V900__fixture_example_item.sql`），**与生产迁移分目录**。
- 后端**零邮件依赖、零邮件配置**（pom 与配置里都检索不到 mail/smtp）。
- 本地已有一条到服务器 MySQL 的 SSH 隧道（`127.0.0.1:3307`），后端以 `local` profile 可正常启动，健康检查为 UP。

### 前端现状（WORK-002 交付）

- 四个应用面：`apps/app`（学习者端，Web 与桌面共用产物）、`apps/admin`（仅 Web）、`apps/public`（公开页）、`apps/ui-kit`（仅开发内审）。
- `packages/core` 已有 `createSessionReader` / `canAccessAdmin`：**从 JWT 载荷读 `role`，读不到或不可识别一律当学习者（失败即拒绝）**；注释已写明客户端解析不校验签名、不是授权边界。
- `apps/app/src/api.ts` 与 `apps/admin/src/api.ts` 都用 `getToken: () => null`——这是接入认证的唯一接缝。
- `apps/admin` 已有 `RequireAdmin` 守卫与 `AdminDenied` 页，因后端不签发角色而**恒为拒绝**。
- 学习者端没有任何登录概念，首页直接展示后端接口的真实返回。
- 桌面端 `Platform.cache` 的同步读缺陷已修（`createBridgeCache` 由启动快照初始化镜像），主题偏好可跨重启保持。

### 已裁决且本项必须遵守的既有决定

- D-10：**自签 JWT**，且必须收在单一模块的端口之后以保持可扩展。
- **会话 Cookie 被排除**（桌面壳页面来源非 http(s) 域，`SameSite`/`Secure` 语义失效）；因此认证令牌一律走 `Authorization` 头。
- 编码约定：所有 SQL 只在 mapper 中、时间统一存 UTC、标识符小写 snake_case、主键数据库自增（D-05）。
- 公开仓库保密规则：凭据不得写入任何被 Git 跟踪的文件。

## 用户决定

以下均由用户在 2026-10-09 逐项裁决。

1. **有密码**：登录用密码，不是无密码登录。
2. **注册需要邮箱验证码**，且**发送邮箱验证码之前必须先通过图形验证码**（图形验证码的作用是保护发信接口，不是保护登录）。
3. **注册资料**：用户名 + 邮箱 + 密码。
4. **登录标识**：**用户名与邮箱都能登录**，两者各自唯一。
5. **面向所有人开放**：不做年龄门、不做监护人同意链路。
6. **令牌方案**：短 access + **refresh 轮换**（不采用单一长 TTL）。
7. **前端结构**：抽一个共享包放登录/注册表单、会话状态与 401 统一处理；学习者端与管理端**各自持有登录页**（登录后跳向哪里由各 app 决定）。
8. **整个学习者端都要登录**：未登录访问一律导向登录页。
9. **图形验证码自建**（后端生成图片 + `captchaId` 关联答案），不接第三方验证码服务。
10. **邮件本期就接真实 SMTP**。
11. **找回密码本期不做**。
12. **传输层不要求 HTTPS，明文 HTTP 即可**（2026-10-09 用户决定，豁免了先前列为风险的那一项）。**后果按原样记录**：密码与令牌在网络上明文传输，链路上任何一环都能读到；浏览器也会对登录页显示"不安全"。前端服务端与后端将来若只把一端换成 HTTPS，浏览器会因混合内容直接拦掉请求，所以**将来要上就两端一起上**。触发重评的条件：一旦对外网开放、或出现不只有自己使用的真实凭据。

## 实现选择

以下由 Agent 在已批准边界内决定并记录理由；不是需要用户重新裁决的产品范围。

- **access 只放内存、refresh 落盘**。access 放内存使 XSS 无法跨刷新拿到它；refresh 必须跨刷新与跨重启存活，因此走 `Platform` 端口（Web 落 `localStorage`，桌面落主进程缓存）。**代价是已知并接受的**：XSS 仍可读到 refresh，轮换买到的是"单个 access 寿命很短"与"盗用后可经重用检测发现"，买不到"XSS 拿不到令牌"。
- **令牌有效期**：access 15 分钟、refresh 14 天，均可配。
- **密码哈希用 BCrypt**（Spring Security 自带，零新增依赖）。
- **图形验证码与邮箱验证码的短期状态、以及限流计数，都放进程内存储并带 TTL 与容量上限**。理由：当前是单实例自托管。**天花板已标注**：多实例部署时三处都必须换成共享存储（DB 或 Redis），代码里标注升级路径。
- **注册请求直接携带邮箱验证码，由注册接口一次性校验**，不引入"先验证再发注册票据"的额外状态。
- **登录失败信息不区分"账号不存在"与"密码错误"**，统一文案；但**注册时会明确告知用户名/邮箱已被占用**（否则用户无从得知该登录），这条取舍写进设计。
- **邮箱在注册时即标记为已验证**（`email_verified_at`），因为注册本身就走验证码。
- **注册出来的一律是学习者角色**；管理员只能由 dev/测试种子迁移或运维手段产生。
- **种子账号只放 `classpath:db/testdata`**（与既有夹具同目录），**绝不进生产迁移**，且密码哈希是固定的测试值。
- **登出 = 吊销该 refresh 记录 + 前端清空 access**；JWT 无状态，因此 access 在其剩余寿命内仍然有效，这点写进设计而不是假装已解决。
- **前端令牌读取仍收在 `getToken` 一处**（沿用 WORK-002 的接缝），401 处理收在共享包一处。

## 背景

WORK-001 定了"自签 JWT + 收在端口后"，WORK-002 把前端拆成四个面并给了角色判断的端口，但后端**至今没有任何账号**：唯一的签发端点不校验凭据、只在 dev/local 存在。因此学习者端完全开放、管理端恒被拒绝，而这个平台的核心（每个学习者有自己的学习者模型与学习路径）**根本无法开始**——没有身份就没有"我的"。

本项要交付的是这个平台的第一块信任地基：账号从哪来、凭据怎么存、身份怎么在前后端之间传递、失效怎么恢复。

## 目标

让用户能注册与登录，让前端能可靠地持有与刷新身份，让后端能按身份与角色授权，并把这条链路的安全基线（密码存储、验证码、限流、撤销、错误信息）落在可验证的自动化检查上。

## 非目标

- 不做找回密码、修改密码（修改密码涉及登录后接口，等第一个真的需要它的场景）。
- 不做第三方登录（OIDC / 微信等）——但端口必须留出接入位置。
- 不做邮箱之外的验证方式（短信、TOTP）。
- 不做未成年人年龄门与监护人同意（用户已明确：面向所有人开放）。
- 不做多因素认证。
- 不做用户资料管理（头像、昵称修改等业务属性）。
- 不做管理端的具体管理功能（只把守卫接上真实会话）。
- 不做部署与 HTTPS 落地（但必须写进风险与「待确认问题」）。

## 用户与工作流程

- **新用户**：在登录页转注册 → 填用户名、邮箱、密码 → 过图形验证码 → 收邮箱验证码 → 提交注册 → 直接进入已登录状态。
- **老用户**：填用户名或邮箱 + 密码 → 登录 → 进入学习者端。
- **已登录用户**：access 过期时前端自动用 refresh 换新；refresh 也失效（过期、被吊销、检测到重用）时回到登录页并说明原因。
- **管理员**：用种子账号登录 → 管理端守卫放行。

## 功能需求

- REQ-001 **账号实体**：必须有账号表，含唯一用户名、唯一且已验证的邮箱、密码哈希、角色、以及创建/更新时间；用 Flyway 迁移建立，遵循既有主键、时间与命名约定。
- REQ-002 **注册**：必须支持"用户名 + 邮箱 + 密码 + 邮箱验证码"的注册；**邮箱验证码只能在其同批请求通过图形验证码校验之后才被发送**；用户名或邮箱重复必须被拒并明确指出是哪一个。
- REQ-003 **登录**：必须支持用**用户名或邮箱**加密码登录，成功后返回 access 与 refresh。
- REQ-004 **令牌轮换**：refresh 必须一次性使用；每次刷新签发新的 refresh 并作废旧的；**旧 refresh 被再次使用时必须失败，并使该 refresh 所属的整条链失效**（重用检测）。
- REQ-005 **登出与撤销**：必须支持登出，使该 refresh 立即不可用；access 的剩余寿命问题必须被明确说明而不是回避。
- REQ-006 **角色**：签发的令牌必须携带角色；`AuthPort.Subject` 必须带角色；注册产生的一律是学习者；管理员只能由种子或运维产生。
- REQ-007 **前端共享认证包**：必须有一个共享包承载令牌存储、刷新调度、401 统一处理与登录/注册表单；**业务页面不得直接操作令牌**。
- REQ-008 **两端登录门**：学习者端整体要求登录（未登录导向登录页，登录后回到原目标地址）；管理端守卫必须接上真实会话，仍只放行管理员。
- REQ-009 **图形验证码**：后端必须能下发图片与 `captchaId`，并支持前端点击刷新；校验必须一次性、有有效期；**不依赖 Cookie 或会话**（与既定的无状态、桌面壳无 Cookie 相容）。
- REQ-010 **邮件发送**：必须能真实发出带验证码的邮件；SMTP 参数与凭据只来自配置（本地凭据放被忽略的配置文件），且发送能力必须收在一个可替换的端口之后。
- REQ-011 **限流**：必须有自动化检查证明以下三条在超过阈值后被拒：同邮箱的发信频率、单个验证码的尝试次数、同账号或同来源的密码登录失败次数。
- REQ-012 **关闭裸签发端点**：现有不校验凭据的 `POST /api/v1/auth/token` 必须在非 dev/local 环境不存在，且有自动化检查证明。
- REQ-013 **安全基线**：密码只存哈希；邮箱验证码与图形验证码答案只存哈希；日志与错误响应不得包含密码、令牌或验证码；登录失败响应不得泄露账号是否存在。

## 质量要求

- **可测试性**：注册全链路、登录成功与失败、refresh 轮换与重用检测、登出、三条限流、以及"裸签发端点在非 dev 环境不存在"，各有一条可本地执行的自动化检查。
- **可维护性**：身份验证与令牌签发分离——本期验证方式是"密码"与"邮箱验证码"，将来加第三方登录或 TOTP 时不得改动令牌那一层。
- **可诊断性**：登录与刷新的失败原因在服务端日志里可区分（令牌过期 / 签名无效 / refresh 已吊销 / 检测到重用），但**对外部的响应不区分**。
- **可访问性**：登录与注册表单的字段有标签、错误与焦点状态由既有设计系统提供，键盘可完整完成注册与登录。
- **前端一致性**：登录页与注册页使用 WORK-002 的设计系统与令牌，不引入新的视觉语言。

## 约束与依赖

- 遵守 D-10：令牌机制收在 `paideia-security` 的端口之后；业务模块不得直接依赖 `AuthPort` 以外的令牌细节，也不得依赖 Nimbus/JWT 类型。
- **认证令牌一律走 `Authorization` 头**，不得引入会话 Cookie。
- 账号表与迁移必须遵守既有约定：SQL 只在 mapper、时间存 UTC、小写 snake_case、主键自增、审计时间用 MySQL 列默认值。
- 新增凭据（SMTP 授权码、签名密钥）**只能进被忽略的本地配置文件或环境变量**，仓库内只提交占位示例。
- 前端不得绕过共享认证包直接读写令牌；`packages/ui` 仍不得引用 `core` 或平台包（WORK-002 的边界检查继续生效）。
- 学习者端现有的三条 e2e 会因为"整个端要登录"而失效，**必须改造成"先登录再断言"，而不是删除**；这需要一个种子账号。

- AC-001：Flyway 迁移在 MySQL 上执行通过，账号表含唯一用户名与邮箱索引、密码哈希列、角色列与审计列；`local` profile 启动后 `/actuator/health` 仍为 UP。

- AC-006：前端 e2e 证明：未登录访问学习者端被导向登录页；登录后可达并展示真实数据；管理端对非管理员仍被拒、对种子管理员放行。
- AC-007：前端自动刷新有自动化检查；refresh 失效时回到登录页并有可见原因。
- AC-008：三条限流各有自动化检查证明超过阈值后被拒。
- AC-009：非 dev/local profile 下裸签发端点不存在（有自动化检查；可采用"该 profile 下路由不存在"或"该 profile 下请求被拒"二者之一）。
- AC-010：四个应用构建通过、`pnpm -r typecheck` 与 `pnpm -r test` 全绿；桌面端产物仍不含管理端；既有边界检查与令牌单一来源检查继续通过。

## 假设

- 单实例自托管部署；因此图形验证码、邮箱验证码与限流计数可以放进程内存储（多实例时必须换共享存储，代码中标注）。
- 平台面向所有人开放，不需要年龄门与监护人同意（用户 2026-10-09 明确）。
- SMTP 由一个可用的发信账号提供，其凭据由用户提供并只写入被忽略的本地配置。
- 首版用户量不大，因此不做容量与性能规划。

（传输层不要求 HTTPS 已由用户在 2026-10-09 决定，见「用户决定」第 12 条，不再是待确认问题。）
