# 账号与认证提案

本提案只处理**账号、凭据与身份传递**。学习路径、内容、学习者模型等业务不在范围内。

## 摘要

在已裁决的技术底座上落地三件事：**一个账号业务模块**（注册、登录、角色）、**一套有状态的 refresh 令牌轮换**（能被撤销、能检测盗用）、**一套前端共享认证包**（令牌存储、自动刷新、401 统一处理，两个应用各自挂登录页）。同时把图形验证码与邮箱验证码做出来，并把发信隔离在一个端口之后——这样"SMTP 凭据最后再给"不会卡住中间任何一步的验证。

## 推荐方案

### 1. 新增业务模块 `paideia-account`，账号不进 security

`paideia-security` 是认证授权**基础设施**（令牌、安全装配、当前用户上下文），它有 `AuthPort` 但**不认识账号表**。账号是业务实体，将来 `learning` 等模块要按 `userId` 关联数据时，它们应该依赖账号模块而不是安全基础设施。

因此：`paideia-account` 拥有 `users` 表、注册与登录用例、图形验证码与邮箱验证码；它依赖 `paideia-security` 的 `AuthPort` 来签发令牌。依赖方向是 **account → security**，security 永远不知道账号的存在。

**代价（已知并接受）**：多一个 Maven 模块与一份 pom。WORK-001 已记录"业务模块边界比包边界难改"，所以这是趁需求明确时一次做对，而不是先塞进 security 以后再抽。

### 2. refresh 用不透明随机串 + 状态表，不用 JWT

JWT 无状态，因此**无法撤销**；而"短 access + refresh 轮换"的全部价值就在撤销与重用检测上。所以 refresh 是一个 256 位随机串，数据库只存它的 SHA-256 哈希：

```sql
refresh_tokens(
  id, user_id, token_hash UNIQUE, family_id,   -- family 用于"整条链"吊销
  expires_at, revoked_at, created_at
)
```

流程：登录签发 access（JWT，15 分钟，带 `sub` + `role`）与 refresh（14 天）；刷新时旧 refresh 立即置 `revoked_at`（一次性）；**若已吊销的 refresh 被再次使用，判定为盗用，吊销该 `family_id` 下全部记录**。登出吊销整条 family。

**必须写明的天花板**：access 无状态，所以登出后它在剩余寿命（≤15 分钟）内仍然有效。这个窗口是选择 JWT 的固有代价，不回避、不假装已解决。

### 3. 令牌传输与存放

access **只放内存**、refresh **落盘**（走既有的 `Platform` 端口：Web 落 `localStorage`，桌面落主进程缓存）。桌面壳的来源不是 http(s) 域，会话 Cookie 已被 D-10 排除，所以两端都只能走 `Authorization` 头——这与既有决定一致，不需要新裁。

### 4. 图形验证码用 `captchaId` 关联，不用 session

图形验证码天生需要"服务端记得答案"，传统做法靠 session + Cookie 关联。本项目 `STATELESS`、禁用 Cookie、桌面壳更是用不了 Cookie，**所以 `captchaId` 不是三个备选之一，而是唯一自洽解**：后端出图时给一个不透明 ID，按 ID 存答案哈希与有效期，提交时带回，校验后立即作废。

后端用 Java2D 自行出图（4 位、去掉易混字符、加干扰线），零外部依赖零成本。

### 5. 邮箱验证码与发信：端口隔离，凭据最后接

发信收在一个 `MailPort` 之后，两个实现：

| 实现 | 用途 |
| --- | --- |
| 日志实现 | 开发期：验证码写日志，不出网；未配 SMTP 时的默认 |
| SMTP 实现 | 真实发信；参数与凭据只来自配置 |
| 内存信箱实现 | **测试期**：集成测试直接读到明文验证码，不依赖网络与真实邮箱 |

这样注册链路的正确性（验证码一次性、过期、尝试次数、限流、占用判定）**全部由集成测试证明，不需要真实 SMTP**；用户最后提供凭据时，只需启用 SMTP 实现并发一封确认信。

### 6. 注册流程与枚举防护的顺序

`POST /api/v1/auth/register` 的顺序刻意如此：**先校验邮箱验证码（证明他控制该邮箱）→ 再查用户名/邮箱占用 → 再插入**。这样"这个邮箱已被注册"只会告诉一个已经能收到该邮箱邮件的人，把账号枚举的成本抬到"先通过图形验证码 + 收到信"。数据库的唯一索引兜底并发，捕获冲突后转成明确的业务错误。

### 7. 前端 `packages/auth`：令牌与 401 只写一份

- **access 在内存 + refresh 走注入的存储**；业务页面不得直接碰令牌。
- **401 自动刷新**：包装 `fetchImpl`（`createApiClient` 已有这个注入点，不必改 core）——收到 401 → 刷新一次 → 重放原请求；刷新失败 → 清令牌并通知认证上下文回登录页。**并发 401 只发一次刷新请求**（共享同一个 in-flight Promise），否则十个并发请求会打十次刷新，而 refresh 是一次性的，后九个必然失败。
- 登录页与注册页**放在各应用里**（登录后跳向哪里、这个应用要不要登录，是应用的策略）；表单与会话逻辑放共享包。
- 学习者端整体加登录门：未登录导向登录页并记住目标地址，登录后回原地址。

### 8. 关掉裸签发端点：直接删除

`POST /api/v1/auth/token` 不校验任何凭据、可为任意主体签发令牌，只在 dev/local 存在。有了真实登录之后 dev 也不再需要它（e2e 用种子账号登录），**所以直接删除**，而不是"只在生产禁用"——一个不该存在的东西留着就是隐患。

### 9. 限流：从"加分项"变成必需项

发信接口是新的滥用面（烧发信配额、被拉黑），验证码是可爆破面（6 位数字），密码登录是暴破面。三条都要有：同邮箱发信间隔与每小时上限、单码尝试次数上限、登录失败按账号与来源计数。实现用**进程内计数 + TTL + 惰性清理 + 一个定时清理任务**（单实例自托管够用），**多实例部署时必须换共享存储，代码里标注升级路径**。

## 范围

包含：`paideia-account` 模块、`users` 与 `refresh_tokens` 两张表与迁移、注册/登录/刷新/登出/图形验证码/发信六个端点、`AuthPort` 带角色、删除裸签发端点、三条限流、`packages/auth`、两个应用的登录与注册页、学习者端登录门、既有 e2e 改造、种子账号（仅 dev/测试）。

不包含：找回密码、修改密码、第三方登录、短信/TOTP、年龄门与监护人同意、用户资料管理、管理端的具体管理功能、部署与 HTTPS。

## 备选方案

**账号放进 `paideia-security`，不新建模块。** 最强的一面是文件少、不用加 pom，账号与令牌天然在一起。未选理由：`security` 是基础设施，`users` 是业务实体；将来按 `userId` 关联学习数据时，业务模块会想依赖"账号"而不是"安全装配"，那时再抽出来要动更多地方。代价：多一个模块与一份 pom。

**refresh 也用 JWT（纯无状态）。** 最强的一面是完全不用状态存储，扩容无痛。未选理由：那样"轮换"只是发新令牌，旧令牌仍然有效到过期，**撤销与盗用检测都做不到**——而这两点正是用户选 refresh 轮换的目的。

**图形验证码接第三方（极验/腾讯天御/阿里云）。** 最强的一面是抗爆破与体验最好，且不用自己维护出图逻辑。未选理由（用户 2026-10-09 裁决）：自建零依赖零成本、数据不出内网。代价：需要自己写生成与过期逻辑，且能被 OCR 破解，所以限流是必须的配套。

**用 session/Cookie 关联图形验证码。** 未选：与"无状态 + 无 Cookie"决议直接冲突，桌面壳还会因 `SameSite` 失效而挂。

**把图形验证码与邮箱验证码的短期状态放进 MySQL 表。** 最强的一面是多实例可用、重启不丢。未选（本期）：单实例自托管下引入两张带 TTL 的表与清理逻辑，成本大于收益；升级路径已标注。

**找回密码本期一起做。** 未选（用户 2026-10-09 裁决）：本期不做。

## 风险与缓解措施

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 并发 401 打多次刷新，而 refresh 一次性 → 后到的刷新全部失败 | 高（随机掉登录，难复现） | 前端共享一个 in-flight 刷新 Promise；集成测试覆盖"并发两个请求同时 401" |
| 登出后 access 在剩余寿命内仍有效 | 中 | 这是 JWT 固有代价，明确写进设计与需求；access 寿命压到 15 分钟 |
| Java2D 在无头服务器上因缺字体/字体配置而出图失败 | 中 | 只用数字与字母（走 JDK 内置逻辑字体）；启动即验证一次出图；失败时明确报错而不是静默 500 |
| 进程内限流与验证码状态在重启后丢失 | 中 | 已知并接受（单实例）；影响只是用户需要重新获取验证码；多实例升级路径已标注 |
| 种子账号带固定密码哈希 | 中 | 只进 dev/测试迁移目录，生产迁移不含；e2e 跑在 `paideia_test` 库而不是 `paideia` 库 |
| 无 HTTPS，密码与令牌明文传输 | 高（用户已明确豁免） | 已记入需求与 `always.md`；触发重评条件写明（对外网开放或出现他人真实凭据） |
| 本项把学习者端整体关进登录门，破坏了既有 e2e | 中 | 改造而不是删除：新增"先登录再断言"的用例并保留原有断言；种子账号由迁移提供 |
| 没有 HTTPS 也没有管理员接口，管理端的越权拦截仍只在后端之外 | 中 | 本期后端只提供角色，不提供按角色拒绝的接口（没有消费者）；**这一条必须在报告里写明是缺口** |
