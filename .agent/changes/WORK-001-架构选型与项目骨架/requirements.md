## 背景

Paideia 要做「千人千面的 AI 个性化学习平台」，不是把同一套课程分发给所有人后只显示不同进度条。这要求学习者模型成为一等实体，内容与服务围绕单个学习者现场编排：学习路径、讲解粒度、练习难度、反馈方式随人变化。仓库目前为空，架构形态一旦落地会约束之后所有工作项，因此必须在写业务代码之前定下来并留下可复审的依据。

## 目标

确定 Paideia 的整体架构形态与数据访问策略，并落地一个可运行、边界受自动化约束的项目骨架，使后续功能开发有稳定且可演化的地基。

## 非目标

- 不在本工作项实现任何具体业务功能（不做课程、练习、登录以外的学习功能）。
- 不在本工作项接入真实大模型生产流量；AI 相关只做到架构就位与单点连通验证。
- 不追求第一版就支持全部目标数据库；只要求 MySQL 完整可用且切换路径真实存在。
- 不做性能压测与容量规划。

## 功能需求

- REQ-001：必须选定一个明确的整体架构形态，并以可复审的形式记录备选方案、各自成立的理由、未选理由、代价与重审条件。
- REQ-002：架构必须承载平台的核心能力——每个学习者拥有独立的学习者模型（已掌握/未掌握的知识点、目标、当前进度），系统据此决定其下一步内容与练习。
- REQ-003：数据访问层必须支持多数据库。在 MySQL 上完整实现并验证；切换到另一种数据库时不需要重写业务逻辑代码。
- REQ-004：必须交付可运行的端到端骨架：后端能构建并启动并提供至少一个接口；前端能启动并成功调用该接口展示真实返回数据。
- REQ-005：模块边界必须有构建期自动化检查，出现非法跨模块依赖时构建失败，而不是靠代码评审约定。
- REQ-006：涉及学习者数据的存储必须先定义隔离维度（租户/用户），并有自动化检查防止一次请求读到不属于它的数据。

## 质量要求

- 可维护性：模块边界由工具在构建期强制；跨模块通信有单一入口，不出现散落的直接调用。
- 可演化性：将来把某个模块拆成独立服务时，不需要重写该模块的业务逻辑——模块间契约已经以事件或 API 形式存在。
- 可测试性：边界约束与数据隔离各有一条自动化检查，能在本地一条命令内复现。
- 可诊断性：数据访问层在启动时暴露实际解析出的数据库方言，避免方言匹配失败被静默吞掉。

## 验收标准

- AC-001：架构决策文件覆盖不少于 5 种备选形态，每个备选写明其成立理由、未选理由、代价和重审条件；结论经用户确认。
- AC-002：后端骨架在 JDK 25 上能构建并启动，健康检查端点返回 UP，且该结果有一次可复查的运行记录。
- AC-003：前端骨架能启动并成功调用后端接口，界面上展示的是接口真实返回的数据（不是硬编码）。
- AC-004：模块边界校验在构建流程中自动执行；人工引入一次非法跨模块依赖时构建失败，并留下这次验证记录。
- AC-005：至少一个仓储层用例在 MySQL 上通过，且其 SQL 不含被列为不可移植的语法（数据库自增主键取值、upsert、`SKIP LOCKED`、`MERGE`、`RETURNING`）；分页由方言抽象产生而非 `RowBounds`。
- AC-006：存在自动化检查，能证明用户 A 的请求无法读到用户 B 的数据。

## 假设

- 开发者为单人或小团队，没有足以独立运维分布式系统的规模；这是选择架构形态时的重要前提。
- 第二种数据库属于「要求具备切换能力」而非「近期实际部署」；若用户实际计划短期内同时运行两种数据库，约束强度需要重新确认。
- 前端第一版只有一个 Web 客户端，暂无原生移动端。

## 待确认问题

1. **架构形态**（阻塞）：模块化单体 / 服务化 / 微服务，需用户选定。
2. **多租户模型**（阻塞）：共享表加租户列（最省）、按租户分 schema、还是按租户分库。选择同时决定隔离强度与运维成本。
3. **向量检索方案**：MySQL 社区版不能原生做向量排序，是否引入 pgvector 或独立向量库；若引入 pgvector 则与「MySQL 起步」存在张力，需要用户裁决。
4. **AI 引擎**：Spring AI 还是 LangChain4j。
5. **前端形态**：Vite SPA 还是 Next.js（取决于是否存在公开课程页/营销页的 SEO 需求）。
6. **多数据库范围**：需要实际部署并验证第二种数据库，还是只保留可切换能力即可。
7. **仓库结构**：单仓多模块（前后端同仓）还是前后端分仓。
