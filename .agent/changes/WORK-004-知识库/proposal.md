# 知识库提案

本提案只处理**知识内容的存储、组织、检索与浏览**，以及**管理端的写入路径**。AI、Agent 运行时、个人笔记不在范围内（见需求文末的拆分说明）。

## 摘要

新增一个业务模块 `paideia-knowledge`，拥有三张表（层级分类、知识条目、条目关系），对外提供两组端点：一组给学习者只读浏览（分类树、条目列表、条目详情、关系邻域、检索），一组给管理端写入（分类、条目、关系，只对管理员开放）。学习者端加两个页面（知识库列表与条目详情），管理端引入路由并加一个知识库管理区。同时**补上后端一直缺失的角色拒绝规则**——这是本项最容易被漏、后果最重的一处。

## 推荐方案

### 1. 新增业务模块 `paideia-knowledge`，不塞进 account 或 security

`security` 是认证基础设施、不认识业务表；`account` 拥有 `users`。知识库是第三个业务实体，按 WORK-003 已确立的判断（"账号是业务实体，单独一个模块"）应当自成模块：

- 依赖方向：`knowledge → {platform, persistence, security}`。**不依赖 `account`**——本项只取当前用户身份（`CurrentUser`），不需要账号数据；`AccountApi` 因此仍然没有消费者。
- 模块内按功能纵切（沿用 `paideia-account` 的组织方式）：`internal/category`、`internal/entry`、`internal/relation`、`internal/search`、`internal/web`；**包根只放 `KnowledgeApi`**，且只暴露真实会被别的模块调用的方法——本项预计它一开始是空的或只有极少数方法，不预先设计。

**代价（已知并接受）**：多一个 Maven 模块与一份 pom，且 Maven 声明要加三处（根 pom 的 `<modules>`、根 pom 的 `dependencyManagement`、`paideia-app` 的 `<dependencies>`）——漏第一处不构建、漏第三处运行时不装配。

### 2. 三张表，条目挂单分类，关系用边表

```
knowledge_categories     id, parent_id(自引用), name, slug(唯一), sort_order, 审计列
knowledge_entries        id, category_id(可空), title, body(MEDIUMTEXT, md), status(draft|published), published_at, 审计列
knowledge_entry_relations id, from_entry_id, to_entry_id, relation_type, created_at
```

- `parent_id` 自引用即层级树；`slug` 唯一便于将来做稳定链接。
- 条目**挂单个分类**（可为空 = 未分类）。多分类需要一张关联表，而目前没有任何需要它的场景。
- 关系是**有向边 + 类型**：`prerequisite`（A 是 B 的前置）与 `related`（无向语义，存一条）。用边表而不是往条目表塞 `parent_id`/`related_ids`，因为类型会增多，而 JSON 列里的关系无法被外键与唯一索引保护。
- 迁移编号顺延为 `V2__create_knowledge_tables.sql`，与 `V1` 同目录（生产迁移集中在 `paideia-app`）。

### 3. 检索用 MySQL `FULLTEXT` + `ngram` 解析器

中文内容用 MySQL 默认全文解析器**基本不召回**——它按空格切词，而中文没有空格。社区版上唯一可行解是 `FULLTEXT ... WITH PARSER ngram`：

- 索引建在 `(title, body)` 上；查询用 `MATCH(...) AGAINST(? IN BOOLEAN MODE)`。
- **已知天花板**：ngram 的分词长度默认 2，长度小于该值的查询召回为零；本方案对这类短查询退回 `LIKE '%x%'`，并接受它不快（条目量在数百量级）。这个回退不是"顺便加的"，而是必须的，否则用户搜单个汉字会得到空结果并以为是 bug。

### 4. 关系视图第一版只做"邻域"，不做全局力导向图

需求里写的是"图谱可视化"。做法上分成两件事：

- **邻域视图**（本版做）：当前条目居中，前置与相关条目围绕它，手写 SVG + 分类色，零新增依赖，一屏能读完。
- **全局图谱**（本版不做）：需要图布局库（力导向或分层），且几百条边以上在浏览器里既慢又读不懂。

未选全局图的理由不是"做不到"，而是**本版真正的用户问题**是"这条知识的前置是什么、相关的是什么"，邻域视图直接回答它；全局图回答的是"整个知识库长什么样"，在本版内容量下没有决策价值。

### 5. 补上角色拒绝：在过滤器链上加一条路径规则

这是本项最关键的改动，也是最大的风险点。现状：`SecurityConfiguration` 只放行业务无关路径，其余 `anyRequest().authenticated()`，**角色从未被用来拒绝任何请求**。

做法是在 `SecurityFilterChain` 里、`anyRequest()` 之前加：

```
.requestMatchers("/api/v1/knowledge/admin/**").hasRole("ADMIN")
```

**为什么用路径规则而不是 `@PreAuthorize`**：路径规则只有一处，新增管理端接口时**默认就被保护**；方法注解要求每个新方法都记得加，漏一个就是一个越权写入点。代价是规则较粗——将来若出现"管理员可写、学习者可写自己那一份"的接口，需要回到方法级。

**顺序陷阱**：`/api/v1/knowledge/admin/**` 的规则必须排在 `/api/v1/knowledge/**` 之前；Spring Security 按声明顺序匹配，顺序反了管理员规则永不生效。

### 6. 前端：新增共享包 `packages/knowledge`，两个应用各有页面

两个应用都要消费同一组类型与同一个 md 渲染器，所以放共享包（与 `packages/auth` 同一层）：

- `packages/knowledge`：DTO 类型、`createKnowledgeApi(client)`、以及 `MarkdownBody` 组件。
- `apps/app`：新增 `/knowledge`（列表 + 分类树 + 搜索框）与 `/knowledge/entries/:id`（详情 + md 渲染 + 邻域）。
- `apps/admin`：**引入 `react-router`（Hash 路由）**，保留现有单屏为 `/`，新增知识库管理区。

**md 渲染用 `react-markdown` + `remark-gfm`**：它把 markdown 转成 React 元素而不用 `dangerouslySetInnerHTML`，注入风险在构造上被排除；`marked` + `dompurify` 需要自己保证消毒正确，多一个可错的环节。这是本项**唯一新增的前端依赖**。

**不要忘记**：`packages/knowledge` 含 `.tsx`，必须在 `globals.css` 里补一行 `@source`，否则它独有的 Tailwind 类名会静默不生成（WORK-003 踩过一次）；`source-coverage.test.ts` 会拦。

### 7. 本地文件存储：端口 + 一张文件表，读取端点不鉴权

附件（图片、PDF）存**服务器本地目录**，但业务代码只依赖一个窄端口

```
FileStorage   put(bytes, contentType) -> id ；read(id) -> bytes + contentType ；exists(id)
```

本版只有一个实现 `LocalFileStorage`（写本地目录）。将来换 S3／OSS／MinIO 只替换这一个实现——这正是用户要的"可扩展、暂时只用本地"。

**文件不是磁盘上的裸文件，而带一条数据库记录**：`knowledge_files(id UUID, original_name, content_type, size, uploader_id, created_at)`。两个理由：

- 读取时按 id **查表再拼路径**，路径穿越从构造上不可能（id 不是用户拼出来的路径片段）；
- 返回 `Content-Type` 用**入库时嗅探到的类型**而不是客户端声明的类型，避免把浏览器带进错误解析。

**读取端点不鉴权**（用户 2026-10-10 裁决）。这是一个被迫的取舍而非偏好：

| 做法 | 结果 |
| --- | --- |
| 端点鉴权 + 前端 blob 取图 | 安全一致，但要给 md 渲染器写自定义 `img`、每图多一次请求、失去浏览器图片缓存 |
| **端点公开 + UUID 文件名（采用）** | `<img>` 直接可用、浏览器能缓存；代价是未发布条目引用的图片 URL 一旦泄露即可被读 |

缓解：文件名是 UUID、不可枚举、不提供目录列举。**必须写明的天花板**：这不是"未发布内容也被保护"，正文受保护、附件不受；接受它是因为附件是管理员录入的内容资产，与已发布内容同一信任级。

**正文里存稳定标识**（`/api/v1/knowledge/files/<uuid>`）而不是绝对地址，渲染时由前端补 baseUrl——桌面壳来源是 `127.0.0.1:5310`，与后端不同源，绝对地址存死会两端失效。

**上传只对管理员开放**，与内容录入同一权限。白名单 `png/jpeg/webp/gif/pdf`，单文件 10 MB 上限，MIME 嗅探与扩展名双重校验，**拒绝 SVG**（可内嵌脚本）。

### 8. 阅读辅助与草稿预览：全部在前端做，零新增依赖

- **正文目录**：渲染 md 时给标题生成 id（自写十几行 slug 函数），再生成目录做锚点跳转。**不引入 `rehype-slug`**——它只解决"给标题一个 id"，为这件事多一个依赖不划算。
- **上一篇／下一篇**：在条目详情响应里直接带上同分类内的相邻条目（一次查询），不在前端拼。
- **反向链接**：关系读取本来就返回 `dependents`（把当前条目当作前置的条目），本次只是把它从图上的节点变成一段**显式列表**。
- **附件图注与放大**：`img` 用替代文本渲染成图注；点击放大**复用 `@paideia/ui` 的 `Dialog`**，不引灯箱库。
- **草稿预览**：加一个管理员专用的条目详情端点（返回草稿正文与关系），管理端用它渲染**与学习者端相同**的组件——预览之所以可信，就在于它走的是同一段渲染代码，而不是另做一套。
- **分类树展开／筛选**：纯前端状态与过滤，后端仍然只返回整棵树（分类数量极小，前端过滤足够）。

### 9. 学习者自评：一张表、三个端点，落在 knowledge 模块内

这是本项唯一的**用户私有业务数据**，也是学习者模型的第一块砖。刻意做得极小：

```
knowledge_self_assessments(
  user_id, entry_id, level('understood' | 'unsure'), created_at, updated_at,
  UNIQUE(user_id, entry_id)
)
```

- 端点：`PUT /entries/{id}/self-assessment`（upsert）、`DELETE` 同上路径（取消）、`GET /self-assessments`（列出自己标记过的）；条目详情响应里带上**自己的**标记。
- **只有两个状态**（懂了／还不懂）：不做等级、不做权重、不做基于作答的推断——那些属于后续的掌握度子系统。
- 归属一律取自令牌，**他人的标记永不返回**，并有专门的隔离检查。
- 放在 `paideia-knowledge` 内而不是新建模块：它现在只是一张依附条目的标记表，为它建模块、pom 与跨模块依赖是提前投资。**代价与升级路径写进设计**：当作答与掌握度成为独立子系统时，这张表很可能被取代或迁移。

## 范围

包含：`paideia-knowledge` 模块、**五张表**与迁移、两组端点（只读 + 管理写）+ 文件上传与读取 + 学习者自评、`FileStorage` 端口与本地实现、`SecurityConfiguration` 的角色路径规则与文件端点放行、`packages/knowledge`、学习者端两个页面（含正文目录、上一篇／下一篇、反向链接、图注与放大、自评按钮）、管理端路由与知识库管理区（含草稿预览）、后端集成测试、前端 e2e、既有边界检查回归。

不包含：练习与作答、判分、基于作答的掌握度推断、学习路径；AI 与助手、个人笔记与分享；云端对象存储；音视频等大体积媒体；全局力导向图；富文本编辑器；内容版本历史与回滚；孤儿文件的定时清理；知识内容的外部批量导入；多语言；细粒度权限。

## 备选方案

**把知识表放进 `paideia-account` 或不新建模块。** 最强的一面是少一个模块与一份 pom，且本项确实只用到了身份。未选理由：知识库与账号是两个完全不同的业务实体、不同的写入方与生命周期；WORK-001 已记录"业务模块边界比包边界难改"，而 WORK-003 也正是按这条判断把账号单独拆出来的。代价：一个模块的成本。

**条目可以同属多个分类（加关联表）。** 最强的一面是更贴近真实的知识组织（一条内容横跨多个主题）。未选理由（本期）：没有任何已确认场景需要它，而多对多会立刻带来"分类树导航显示在哪一层"的额外产品问题。代价：将来要改需一次迁移 + 导航逻辑调整。

**用 `LIKE` 做检索，不建全文索引。** 最强的一面是零索引、零解析器依赖、行为完全可预测。未选理由：条目量虽小，`LIKE '%x%'` 无法走索引，全表扫描随内容增长线性变差，而全文索引是**现在建最便宜**（表还空着）。代价：引入 ngram 解析器与它的短查询限制。

**关系用 JSON 列存在条目表里。** 最强的一面是少一张表和一次 join，读一条目的关系是一次查询。未选理由：JSON 里的关系无法被外键约束（指向已删条目会悬空）、无法加唯一索引（重复边拦不住），而这两件事在管理端手工录入下都会发生。

**给管理端加 `@EnableMethodSecurity` + `@PreAuthorize`。** 最强的一面是权限声明与接口就在同一个文件里，粒度可以细到方法。未选理由（本期）：路径规则只有一处、默认覆盖新增接口，而管理端接口会持续增加；方法注解的失败模式是"漏加"，且不会在任何测试里失败，只会在某天变成越权写入点。代价：规则粒度较粗。

**用 `marked` + `dompurify` 渲染 md。** 最强的一面是体积极小、可控。未选理由：消毒是安全关键路径，自己保证正确比换一个在构造上就不产生 HTML 的库更贵。代价：`react-markdown` 依赖树略大。

**给管理端内联页面，不引路由。** 最强的一面是当下改动最小。未选理由：管理端要放分类、条目、关系三类界面，且后续必然继续加；不引路由会让 `AdminHomePage` 变成一个状态机，而学习者端已有 Hash 路由先例。代价：管理端新增一个依赖与一次 `main.tsx` 改造。

**接云端对象存储（S3／OSS／MinIO）。** 最强的一面是可扩展、可多实例共享、天然备份、不吃本地磁盘。未选理由（用户裁决）：服务器上没有任何对象存储服务，自托管单实例下引入它是为一个不存在的需求付费；而且**本地与云端在同一个端口之后**，将来替换只换实现。代价：本地磁盘成为容量与备份的单点。

**文件存进数据库 BLOB 列。** 最强的一面是事务一致、备份与数据同源、不用管目录权限。未选理由：BLOB 会把 MySQL 备份体积、`mysqldump` 时间与主库 IO 一起拖起来，而文件天生不适合放进行存储。代价：多一个目录与一份"目录备份不在数据库里"的运维注意项。

**文件端点要求登录，前端取成 blob 显示。** 最强的一面是与"整个端都要登录"完全一致，未发布条目的附件也不外泄。未选理由（用户 2026-10-10 裁决）：`<img>` 不带 `Authorization` 头，要这么做必须前端逐个取图转 objectURL，失去浏览器缓存且每图多一次请求。代价：附件成为唯一的免鉴权读取面，写进了需求与测试计划的已知缺口。

**不建文件表，直接往目录里写 UUID 文件。** 最强的一面是少一张表、少一次查询。未选理由：没有表就只能从 URL 路径直接拼磁盘路径（需要自己保证不穿越），且内容类型只能靠扩展名猜——这两件事都比一张表贵。代价：多一张表。

**自评放在一个新的 `paideia-learning` 模块里。** 最强的一面是"学习者状态"讲得通，将来作答与掌握度天然有地方去，`knowledge` 保持纯内容。未选理由（本期）：现在只有"一条标记"这一件事，为它建模块、pom 与跨模块依赖属于提前投资；而且真正的掌握度子系统一旦成型，这张表大概率被取代，届时该迁的是数据而不是模块名。代价：将来迁移这张表要走一次数据库迁移。

**自评直接做成"作答"（给每条内容配题并判分）。** 最强的一面是一步到位，掌握度有真实原料。未选理由：出题与判分必须一起设计（题目从哪来、谁判、主观题怎么办），而按项目已定的功能分层，出题与判分应由固定管线承担——塞进知识库会让两边都做不好。代价：本版拿到的只是自评，信号比作答弱。

**正文目录用 `rehype-slug`。** 最强的一面是成熟，已处理重复标题与特殊字符。未选理由：它解决的问题只是"给标题一个 id"，自写十几行就够，我们也不需要与 GitHub 完全一致的 slug 规则。代价：重复标题的编号要自己处理（已写进设计）。

**图片放大用灯箱库。** 最强的一面是开箱即用的手势、缩放、多图浏览。未选理由：本版只需要"点开看大图、能关掉"，`@paideia/ui` 的 `Dialog` 已经够用，而依赖里每多一个库就多一份升级负担。代价：没有缩放与手势，够用即可。

**草稿预览另做一套渲染。** 最强的一面是可以顺便加"预览"标记，与学习者端互不干扰。未选理由：预览的全部价值就是"看到学习者看到的样子"，另做一套渲染会让预览说谎——它预览的是另一段代码。代价：预览与学习者端共用渲染组件，改动时两边同时受影响（这正是想要的）。

## 仓库影响

- **新增**：`backend/paideia-knowledge/`（模块）、一个建表迁移（**五张表**，编号取实施时目录内的下一个可用值；+ e2e 种子 `db/devdata/V951__seed_knowledge.sql`）、`frontend/packages/knowledge/`、`apps/app` 两个页面与路由、`apps/admin` 的 `router.tsx` 与管理区页面、后端集成测试、前端 e2e。
- **新增（配置与目录）**：上传目录路径的配置项（本地 profile 指向服务器本地目录，**在仓库之外且不被 Git 跟踪**）；该目录不进版本库，也不需要迁移。
- **修改**：`backend/pom.xml`（两处清单）、`backend/paideia-app/pom.xml`、`paideia-security/.../SecurityConfiguration.java`（加角色路径规则，并放行文件读取端点）、`apps/admin/package.json` 与 `main.tsx`、`apps/app/src/router.tsx`、`packages/ui/src/styles/globals.css`（补 `@source`）。
- **不受影响**：`paideia-account`（`AccountApi` 仍无消费者）、`paideia-persistence` 既有机制、`apps/public`、`apps/ui-kit`（可选：展览页加一节展示 md 渲染）。

## 风险与缓解措施

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| **管理端写接口忘了加角色限制 → 任何学习者可写知识库** | 高（数据被任意篡改） | 用路径规则而非方法注解，默认覆盖新增接口；集成测试同时断言匿名 401、学习者 403、管理员 200 |
| 路径规则顺序写反，管理员规则永不生效 | 高（且表现为"看起来配了"） | 规则必须写在 `anyRequest()` 之前；AC-006 的三态测试会直接暴露顺序错误 |
| 中文全文检索不召回（默认分词器不切中文） | 中（用户以为功能坏了） | `WITH PARSER ngram`；短查询回退 `LIKE`；测试用中文关键词断言 |
| `packages/knowledge` 漏登记 `@source` | 中（布局类静默失效，无报错） | `source-coverage.test.ts` 会拦；新增包时同步 `globals.css` |
| md 渲染引入 XSS | 中（内容由管理员录入，但学习者会看到） | 选 `react-markdown`（不产生 HTML 字符串，无需 `dangerouslySetInnerHTML`）；测试断言原始 `<script>` 不被执行 |
| Maven 模块三处声明漏一处 | 中（漏第一处不构建、漏第三处运行时 500） | 在设计里点名三处；AC-001 的启动检查会暴露第三处 |
| 删除分类或条目时关系悬空 | 中 | 外键 `ON DELETE CASCADE`（关系表两端）＋ 分类被引用时拒绝删除并返回明确错误 |
| 管理端引入路由改变现有 e2e | 低 | 现有 `admin.spec.ts` 断言的是 `admin-console`，路由改造后仍应通过；若不通过则修断言而不是删用例 |
| **文件端点不鉴权 → 未发布条目引用的图片 URL 泄露即可读** | 中（用户已明确裁决接受） | 文件名用 UUID、不提供目录列举；写进需求与测试计划的已知缺口；触发重评：出现他人的真实内容或对外网开放时 |
| 上传成为滥用面（塞满磁盘、上传可执行内容） | 中 | 类型白名单 + MIME 嗅探 + 扩展名双重校验、拒 SVG、10 MB 上限、只对管理员开放 |
| 上传目录不可写或磁盘满 | 中（表现为上传静默失败最糟） | 启动时或首次上传时明确报错；失败返回稳定错误码并写日志，不吞异常 |
| 文件表有记录但磁盘文件丢失（或被运维清理） | 低 | 读取时明确 404 并记日志；不做自动修复 |
| 孤儿文件长期累积（删条目不删文件） | 低 | 已知并接受；清理列为已知缺口，条目量级不大时无实际影响 |
| **自评是本项目第一条用户私有业务数据，隔离写错会串号** | 高 | 归属只取自令牌，不接受客户端传 userId；条目详情只返回**自己的**标记；`GET /self-assessments` 按当前用户过滤；有专门的 A/B 隔离自动化检查（AC-013） |
| 自写的标题 slug 遇到重复标题会撞 id | 低 | 设计里要求：同一篇内重复标题追加序号；目录与锚点用同一份 id 生成逻辑 |
| 草稿预览与学习者端共用渲染组件 | 低 | 这正是设计意图（预览必须等于学习者所见）；代价是改渲染时两边同时受影响 |
| 多了自评后，学习者侧不再"只读"，权限面变大 | 中 | 只有这一个写端点且只写自己的数据；AC-006 的三态鉴权与 AC-013 的隔离检查共同守住 |
