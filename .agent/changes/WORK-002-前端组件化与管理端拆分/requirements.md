# 前端组件化与管理端拆分需求

## 已确认事实

### 仓库现状（2026-10-09 读取源码确认）

- 前端是 pnpm workspace：`packages/{ui,core,platform-web,platform-desktop}` + `apps/{app,public,desktop}`。
- `packages/ui` 只有一个占位组件 `Panel.tsx`（内联样式），注释明写"真正的设计系统在后续工作项按需求建立，不在这里提前铺开"。它的消费者有两个：`apps/app/src/pages/HomePage.tsx` 与 `apps/public/src/PublicPage.tsx`。
- `packages/ui`、`packages/core` 等共享包**没有独立构建步骤**：`package.json` 的 `exports` 直接指向 `./src/index.ts`，由消费方（Vite）编译。
- `apps/app` 全站没有任何 CSS 方案，全部是内联 `style`；`vite.config.ts` 已设 `base: './'`（注释写明不能改成 `'/'`），并有 `/api`、`/actuator` 开发期代理。
- 路由是 `createHashRouter`，只有一个 `'/'` 路由指向 `HomePage`。
- `apps/app/src/main.tsx` 是组合根，按 `import.meta.env.MODE === 'desktop'` 选择 `createDesktopPlatform()` 或 `createWebPlatform()`。
- `packages/core` 已定义 `Platform` 端口，当前只有两个成员：`kind` 与 `cache: KeyValueCache`（`get`/`set`/`remove`）。注释明确"文件读写、深链、自动更新等能力等出现需求再加"。
- 已有一条自动化边界检查 `packages/core/src/workspace-boundaries.test.ts`：扫描共享包 `core`、`ui` 的 `src`，禁止出现 `electron`、`@tauri-apps/` 的 import。
- `apps/desktop` 是 Electron 壳，消费 `apps/app` 的构建产物；`apps/public` 是预渲染公开页，有自己的 vite 配置（`noExternal: ['@paideia/ui']`）。
- 没有任何主题机制、没有设计令牌、没有深色模式。

### 联网核实（2026-10-09，结论与来源见本次调研记录）

- **shadcn/ui 仍是"复制源码进你的仓库"模式**，不是普通依赖。CLI 包名 `shadcn`，当前 **4.21.4**；命令 `pnpm dlx shadcn@latest init|add`。
- shadcn/ui 的**默认基座自 2026-07 起是 Base UI**（官方变更日志），Radix **并未进入维护模式**（官方原文 "Radix is not being deprecated."），两套基座并行发布。需要纠正一个流传的说法：Base UI 1.8.0 是**当前版本号**，不是"成为默认"的那次变更（那次是 1.6.0）。
- CLI 有 `--base base|radix|aria` 可固定基座，有 `--monorepo` 与 `-t vite` 模板。
- **monorepo 支持是官方的**：每个 workspace 各放一份 `components.json`，组件装到哪个包由 `aliases.ui` 决定（因此可以把组件装进 `packages/ui` 而不是 app）。
- **Tailwind CSS 当前 4.3.3**：v4 默认不再需要 `tailwind.config.js`，改为 CSS-first（`@import "tailwindcss"` + `@theme`）；Vite 用 `@tailwindcss/vite` 插件。
- **Tailwind v4 的关键扫描规则**：把源文件当纯文本扫描，因此**源码直出、无构建步骤的包（本仓库的 `packages/ui`）天然兼容**；但自动探测**排除 `node_modules`**，而 pnpm 会把 workspace 包软链进 `node_modules`，所以**跨包必须显式 `@source` 且写物理源码路径**，不能写包名。`@source` 的路径相对于写它的那个 CSS 文件。
- **`backdrop-filter` 已是 Baseline 2024**（全球支持约 97%，Electron 即 Chromium 全支持），风险不在兼容而在两处工程陷阱：① **backdrop root 陷阱**——父级只要出现 `opacity < 1`、非 `none` 的 `filter`/`mask`/`clip-path` 等，就会新建 backdrop root 导致模糊"看似失效"；② 模糊区域越大越贵，不适合长列表逐项使用。
- **`prefers-reduced-transparency` 不是 Baseline**（MDN 标 Limited availability），不能作为唯一降级手段；稳妥降级是 `@supports` + 不透明底色。
- **WCAG AA 正文对比度 4.5:1**（大文本 3:1）。半透明层上文字的有效对比度取决于背后内容，必须按最坏背景计算并对**合成后颜色**校验。
- **中文字体**：Windows 官方可用名是 `Microsoft YaHei` / `Microsoft YaHei UI`（微软官方字体列表）；macOS/iOS 为 `PingFang SC`（本轮未能从主源逐字核实，标为通识）；Linux/Android 为 `Noto Sans CJK SC`。字体回退是**逐字符**的，因此拉丁字体在前、CJK 在后即可，末尾必须保留泛型 `sans-serif`；MDN 明确不建议用泛型 `system-ui` 排版大段文本。
- **CJK webfont 体积**：`@fontsource/noto-sans-sc` 整包 unpacked 体积约 74.5 MB（1905 个文件），说明 CJK 字体必须子集化才能上 Web。
- **Tailwind v4 与 Electron**：无特殊问题（纯 CSS 输出）；但 CSS 里不能出现以 `/` 开头的绝对 `url()`，`base: './'` 必须保持（本仓库已设）。

## 用户决定

- **组件库方向选 A（2026-10-09）**：采用 shadcn/ui（源码进仓库）+ Tailwind CSS v4，基座为 Base UI/Radix 系无样式原语，不用现成外观型组件库（Mantine/AntD 等）。
- **管理端独立成应用（2026-10-09）**：新增 `apps/admin`，与 `apps/app` 同仓、共享组件与状态包；不采用"一个 app 内 `/admin/*` 路由级分面"的形态。
- **浅色 + 深色双主题（2026-10-09）**：不做单主题。
- **界面语言只做中文（2026-10-09）**：本期不引入国际化，不做多语言资源。
- **角色只有两个（2026-10-09）**：管理员与学习者。不存在教师、家长等第三种角色。

## 实现选择

以下是 Agent 在已批准边界内按仓库既有模式做的技术决定，记录理由；不是用户需要重新裁决的产品范围。

- **中文字面走系统字体栈，不引 webfont**。理由：既然只做中文且已核实 CJK webfont 整包约 74.5 MB（需子集化工具链），而系统字体栈零体积、零加载。代价是不同操作系统下字形不同（Windows 雅黑 / macOS 苹方 / Linux Noto）。若将来要统一字形，再引入子集化的思源黑体。
- **主题偏好的持久化复用已有的 `Platform.cache` 端口**，不新增存储机制，也不直接碰 `localStorage`。理由：`packages/core` 已经定义了 `KeyValueCache`，端口本来就为这类本地记忆而设；绕过它会让桌面端与 Web 端出现两套存储路径。
- **图标库用 Lucide**（shadcn/ui 的默认图标库），不额外评估。
- **主题默认值跟随系统（`prefers-color-scheme`），用户显式切换后以其选择为准。**
- **`packages/ui` 的约束保持不变并扩展**：仍是纯展示层，不得引用平台 API、不得含业务语义。管理端与学习者端的差异靠"同一基元 + 不同组合"，不建两套组件库。
- **复合业务组件先留在各自 app 内**，同一个东西出现第三次再上提到 `packages/ui`。理由：现在还没有任何业务页面，提前抽复合组件等于按猜测固化抽象。

## 背景

WORK-001 交付了可运行的前后端骨架，但前端只有"一个占位 `Panel` + 一页内联样式"，设计系统被显式推迟（`packages/ui` 的注释、`.agent/references/technology-options.md` 里 D-15 的「设计系统」条目）。同时 WORK-001 的需求文档把"角色模型：只有学习者本人，还是存在教师、家长、管理员"列为待决定项——这一项现已由用户裁决为"管理员 + 学习者"，而管理端在产品上需要一个独立的前端入口。

本工作项因此要一次解决两件相互咬合的事：**把设计系统真正建起来（令牌 + 组件）**，以及**按角色把前端拆成学习者端与管理端**。之所以放在一起，是因为管理端的形态直接决定组件与令牌要不要按端分叉——先组件化再拆端会返工。

## 目标

让前端从"骨架页"变成"有设计令牌、有可复用组件库、有学习者端与管理端两个可运行应用"的地基，并且不破坏 WORK-001 已确立的双端（浏览器 + Electron 桌面）交付与包边界约束。

## 非目标

- 不实现任何业务功能页面。管理端本期只交付可运行的壳与一个最小页面，用于证明结构成立。
- 不实现后端角色模型与权限落库。前端只留接缝，后端角色契约落地属于后续工作项。
- 不动公开页与 SEO（`apps/public` 除跟随组件库演进外不改；本项不扩展 SEO 能力）。
- 不做国际化、不做多语言资源。
- 不引入 webfont，不做字体子集化流水线。
- 不做离线写入与本地数据同步。
- 不做性能压测。

## 用户与工作流程

- **学习者**：使用 `apps/app`（浏览器或桌面安装包），界面为浅色或深色。
- **管理员**：使用 `apps/admin`（仅浏览器），与学习者端共享同一套组件与令牌。
- **开发者**：新增页面的默认路径是"先找 `packages/ui` 已有组件与令牌，没有再按需求新增"，而不是写内联样式。

## 功能需求

- REQ-001：必须有单一的**设计令牌层**，覆盖颜色、排版、间距、圆角与玻璃层级，并为**浅色与深色各提供一套取值**。令牌只能有一个定义来源。
- REQ-002：`packages/ui` 必须成为真正的组件库，承载从 shadcn/ui 引入并适配到本项目令牌的可复用展示组件。组件不得引用平台 API、不得包含业务语义，必须有类型化的 props 与可访问性基线（键盘可达、焦点可见、语义标签）。
- REQ-003：必须新增 `apps/admin` 作为管理端应用，与 `apps/app` 同仓，共享 `packages/ui` 与 `packages/core`；**管理端不得进入桌面构建产物**。
- REQ-004：必须支持浅色与深色主题切换，默认跟随系统；用户显式切换后跨刷新保持；首屏不得出现主题闪烁（先应用主题再渲染内容）。
- REQ-005：前端必须区分管理员与学习者两种身份，管理端路由只对管理员可达。守卫逻辑收在单一处，身份来源可替换——后端角色契约尚未落地时通过端口/适配器提供，业务组件不得直接判断角色字符串。
- REQ-006：`apps/app` 现有页面必须迁移到新组件与新令牌，删除 `packages/ui` 的占位 `Panel` 与页面内联样式。
- REQ-007：已有的共享包边界检查必须扩展到本项新增的包与目录；桌面构建产物中不得出现管理端入口。

## 质量要求

- **可访问性**：键盘可完整操作核心组件；焦点样式可见；使用语义标签；文本对比度达 WCAG AA（正文 4.5:1、大文本 3:1），对半透明层按最坏背景计算合成后颜色；尊重 `prefers-reduced-motion`。
- **玻璃层降级**：不依赖 `backdrop-filter` 也必须可用——先给不透明/近不透明底色，再用 `@supports` 增强；玻璃层不得嵌套在带 `opacity < 1` 或 `filter` 的容器内（backdrop root 陷阱）；模糊不用于长列表的逐项渲染。
- **可维护性**：令牌与主题的唯一来源在 `packages/ui`；应用侧不得出现硬编码颜色字面量。
- **可测试性**：组件与主题切换有可在本地一条命令内运行的自动化检查；两个应用各有一条能证明"渲染了真实数据"的冒烟检查。
- **可诊断性**：主题与角色的当前取值在运行时可从界面状态确认（不靠读代码猜测）。

## 约束与依赖

- 必须保持 WORK-001 已确立的约束：共享包不得引用桌面壳专有 API；资源路径相对（`base: './'` 不得改成 `'/'`）；路由保持 Hash 路由；平台能力只通过 `Platform` 端口暴露。
- **Tailwind v4 的扫描必须显式登记物理源码路径**：不能依赖自动探测（pnpm 的软链落在 `node_modules` 下会被扫描排除），`@source` 必须写 `packages/...`/`apps/...` 形式，不能写包名。
- 不引入 Next.js；不引入 webfont；不引入现成外观型组件库。
- 共享包继续"无独立构建、直出 TS 源码"，不得为此新增构建步骤。
- 公开仓库保密规则适用：不得把凭据、地址写入任何被跟踪文件（项目常驻规则，此处不重复展开）。

## 关联工作项

- **depends_on: WORK-001（已完成）**。本项直接改造 WORK-001 建立的前端工作区结构（`packages/ui`、`apps/app`、`apps/desktop`）、`Platform` 端口与边界检查。没有 WORK-001 的产物无法实现或验收本项。该依赖已完成，不阻塞。
- 后端角色模型与权限落库目前**没有**对应工作项；本项只在前端留接缝。若后续新建该项，与本项的关系是共享"角色"这一概念契约，届时应检查两边的角色命名与取值是否一致。

## 验收标准

- AC-001：类型检查与单测全绿——`cd frontend && pnpm -r typecheck && pnpm -r test` 通过，且新包与新应用都在覆盖范围内。
- AC-002：令牌单一来源可复查——应用侧检索不到硬编码颜色字面量（令牌定义文件与测试除外），且有自动化检查防止回退。
- AC-003：主题切换可验证——浅/深可切换、刷新后保持、首屏无闪烁；两种主题下各有一条对比度核验记录（含玻璃层上的文本）。
- AC-004：**两个应用都能独立启动并渲染后端真实数据**（非硬编码），各有一条可复查的检查记录。
- AC-005：桌面构建成功，且产物中检索不到管理端入口（有可复查的检索命令与输出）。
- AC-006：非管理员身份无法进入管理端路由，有自动化检查证明。
- AC-007：共享包边界检查覆盖本项新增的包与目录，且人工引入一次违规时检查确实失败（有复核记录）。
- AC-008：玻璃层在无 `backdrop-filter` 支持时有可用的降级形态，有复核记录。

## 假设

- 桌面安装包**不需要**管理端。这是"管理端独立成应用"的直接推论；若将来需要，回到 REQ-003 重新评估。
- 管理员身份不改变学习者端界面（管理员用自己的账号看学习者端时，看到的是普通学习者视图）。
- 主题是纯前端状态，后端不参与，也不需要跨设备同步。
- 开发者是单人，因此组件库只需要满足自用，不追求对外发布能力（不做独立的包版本与 changelog）。

## 待确认问题

以下两项都不改变本项的交付边界，因此不阻断需求批准，记录备查：

1. **后端角色契约何时落地**：角色存哪张表、登录接口返回什么形状。本项只留前端接缝，等该契约出现时对接（届时检查与本项的角色命名是否一致）。
2. **管理端的部署形态**（独立子域还是内网单独部署）。本期不实现部署，但要求管理端构建产物能独立部署，不依赖学习者端的部署形态。
