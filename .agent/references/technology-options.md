# 技术选项登记表

本文是**待用户裁决**的技术选项汇总。每一项只列备选方案与优缺点，**不含推荐结论**；结论由用户给出后，才写入工作项的需求与提案。

本文分四部分：A 通用能力候选清单（与业务无关的技术底座）、B 技术选项登记表、C 选项之间的锁定关系（事实描述，非建议）、D 来源。

## A. 通用能力候选清单

「通用」指**不依赖任何业务需求**就能确定存在的技术能力。业务模块（例如学习、练习、路径）的划分必须等需求明确后再做，本文不涉及。

### 后端通用能力

| 能力 | 职责 | 不依赖业务的原因 |
| --- | --- | --- |
| 基础契约 | 统一返回结构、错误码与异常契约、通用值对象、ID 类型、时间与时区约定 | 任何业务都需要统一的对外契约 |
| 数据访问基础设施 | MyBatis 装配、方言抽象与分页、主键生成器、TypeHandler 注册、审计字段填充 | 由「多数据库适配」这个已定约束直接产生 |
| Web 基础设施 | 统一响应包装、全局异常处理、参数校验、请求上下文与追踪标识、CORS、API 版本管理 | 任何 HTTP 接口都需要 |
| 认证授权基础设施 | 认证方式适配、令牌签发与校验、权限模型与校验注解、当前用户上下文 | 与业务无关，是安全边界 |
| 事件基础设施 | 事务性事件发布、outbox 抽象、事件序列化与重投 | 是「将来可拆分」的地基 |
| 缓存基础设施 | 缓存抽象、多级缓存、失效与穿透策略 | 与业务无关的性能手段 |
| 任务与异步基础设施 | 定时任务、异步执行、重试与幂等 | 与业务无关的执行模型 |
| 可观测性 | 结构化日志、链路追踪、指标、健康检查、审计日志 | 运维需求，与业务无关 |
| 配置与环境 | 分层配置、密钥注入、环境切换 | 任何部署都需要 |
| 文件与对象存储 | 存储抽象（本地/对象存储）、上传下载、内容校验 | 上传下载是通用能力，存什么内容是业务 |
| 模型接入基础设施 | 供应商端口、请求路由、限流、用量与成本记账、提示词模板管理 | 这是「连大模型」的管道，不是「用来做什么」 |
| 国际化 | 文案资源、区域与时区处理 | 与业务无关 |
| 测试基础设施 | 测试基类、容器化依赖、测试数据构造 | 与业务无关 |

### 前端通用能力

| 能力 | 职责 |
| --- | --- |
| 设计系统 | 组件库、主题令牌、可访问性基线 |
| 应用核心 | API 客户端、错误契约、状态管理装配、鉴权适配、缓存策略 |
| 平台适配层 | 平台能力接口（文件、安全存储、深链、更新、缓存）+ 各宿主实现 |

**说明**：上表是能力清单，不是模块划分方案。能力如何合并成模块、模块边界如何强制，属于 D-02 与 D-01 的裁决结果。

## B. 技术选项登记表

### D-01 整体架构形态

| 选项 | 优点 | 缺点 |
| --- | --- | --- |
| 模块化单体 | 一套流水线、一套数据库、无分布式运维成本；重构成本最低；边界切错时纠正代价小 | 需要额外的边界纪律与工具，否则退化为大泥球；单点部署，扩容是整体的 |
| 服务化（4–12 个粗粒度服务共享库） | 拿到大部分可部署性收益；不必按服务拆数据 | 共享数据库成为耦合点，「可独立部署」名不副实；比单体多出多套构建与部署 |
| 微服务 | 独立扩缩容；多团队可独立发布互不阻塞 | 分布式带来的自动化部署、监控、失败处理、最终一致性是持续开销；边界切错后跨服务重构代价极高；需要分布式运维能力 |

**影响面**：决定后续所有模块边界、部署形态、团队协作方式、调试与排查方式。
**事实**：Fowler 的「微服务溢价」认为只有当系统复杂到单体难以管理时才划算；反向案例密集——Segment 将 140+ 服务合并回一个，Istio 将四个控制面组件并成单个 `istiod`，Amazon Prime Video 的音视频监控服务从 serverless 微服务改回单体后成本降约 90%；Khan Academy 迁到 Go 服务后承认服务边界「更慢更脆」；Canvas LMS 至今是 Rails 单体 + React 前端。
**状态**：待用户决定。

### D-02 模块边界的强制手段

| 选项 | 优点 | 缺点 |
| --- | --- | --- |
| Spring Modulith | 构建期校验循环依赖与跨模块访问；内置事件发布注册表（事务性 outbox）；可生成 C4/PlantUML 文档 | 引入框架依赖；对包结构有约定要求；模块划分需按它的模型组织 |
| ArchUnit（含 jMolecules 规则） | 规则完全自定义；只依赖测试库 | 规则需自己写与维护；不做事件、文档、outbox 等运行时能力 |
| 仅代码评审约定 | 零依赖、零成本 | 边界靠人记住，会随时间和人员流动失效 |

**影响面**：决定「边界是否真的存在」，直接决定 D-01 里「可演化」是否成立。
**状态**：待用户决定。

### D-03 后端构建工具

| 选项 | 优点 | 缺点 |
| --- | --- | --- |
| Maven | 约定强、资料与中文社区覆盖广、Boot 官方脚手架默认 | 多模块构建较啰嗦、增量构建慢、扩展要写插件 |
| Gradle | 构建脚本灵活、增量与缓存快、多模块体验好 | 灵活性带来「每个项目一套写法」的问题；调试构建脚本成本更高 |

**影响面**：多模块工程的目录组织、CI 缓存策略、新人上手成本。
**事实**：Spring Boot 4 两者都支持，Spring 团队自身使用 Gradle。
**状态**：待用户决定。

### D-04 仓库结构

| 选项 | 优点 | 缺点 |
| --- | --- | --- |
| 单仓多模块（前后端同仓） | 契约改动一次提交完成；跨端重构原子化；CI 配置统一 | 仓库体积增长；前端与后端构建相互触发；权限粒度粗 |
| 前后端分仓 | 各自 CI 独立、权限与发布节奏解耦 | 接口契约变更多一次同步；跨端改动需两处提交、易不同步 |
| 后端多仓（每个模块/服务一仓） | 与服务化形态天然匹配，独立发布 | 单体形态下反而是负担；跨模块改动要跨仓提交 |

**影响面**：影响 D-01 的拆分成本、CI 设计、版本发布策略。
**状态**：待用户决定。

### D-05 主键生成策略

| 选项 | 优点 | 缺点 |
| --- | --- | --- |
| Snowflake（应用侧，64 位 long） | 跨数据库完全可移植；紧凑、索引友好、近似单调；集群安全 | 需要 worker ID 分配；时钟回拨要处理；会泄露时间信息 |
| UUIDv7 / ULID（应用侧） | 跨库可移植；时间有序，索引局部性远好于 UUIDv4；无需协调 | 128 位比 long 大；列类型在各库不同（需要 TypeHandler）；字符串形式占 26–36 字节 |
| 数据库自增 / 序列 | 数据库原生、实现最简单 | **不可移植**：MySQL 无 `CREATE SEQUENCE`；取值方式各异（MySQL `LAST_INSERT_ID`、PG `RETURNING`、SQL Server `OUTPUT`、Oracle `RETURNING INTO`）；MySQL/SQL Server 上单写入者瓶颈 |

**影响面**：所有表结构；与 D-07 的多库适配深度直接冲突或互补。
**事实**：只有应用侧生成在四类数据库上都成立。Oracle 上 `useGeneratedKeys` 会取不到值。
**状态**：待用户决定。

### D-06 分页实现方案

| 选项 | 优点 | 缺点 |
| --- | --- | --- |
| 自研方言拦截器 | 无 `ThreadLocal`，分页参数显式传递；可只为实际支持的库写两族实现；行为完全可控 | 需自己维护 COUNT 重写与边界情况；约需上百行代码与测试 |
| PageHelper | 开箱即用；方言覆盖广（含达梦、人大金仓、OpenGauss） | 用静态 `ThreadLocal` 存分页状态，官方文档自承「未消费的分页参数会污染后续查询」；COUNT 重写遇 `GROUP BY`/`DISTINCT` 会出错；拦截器内部随 MyBatis 版本跟踪 |
| MyBatis Dynamic SQL | 官方家族库，按数据库正确生成 `limit/offset` 或 `fetch first` | 引入 DSL，改变「手写 SQL」的写法；仍是一层需要学习与复用的抽象 |
| 手写各方言 SQL | 零框架风险、零魔法 | 重复度最高，每个分页查询写多份 |
| `RowBounds` | 无需任何实现 | **不是 SQL 分页**：驱动取回全部结果后在内存中跳过，且不提供 COUNT |

**影响面**：所有列表查询；与「手写 MyBatis」的取向是否一致。
**状态**：待用户决定。

### D-07 多数据库适配深度

| 选项 | 优点 | 缺点 |
| --- | --- | --- |
| 只保留切换能力（当前库做实，不部署第二种） | 结构上留出接缝；不为不存在的需求付税 | 第二种库从未真实运行，接缝是否有效未经验证，真到迁移那天才暴露漂移 |
| 实际部署并持续验证第二种库 | 接缝经过真实检验，迁移风险大幅下降 | 双份 DDL、双份集成测试、双份 CI 与数据环境；SQL 被锁在方言最小交集，当前库的高级特性全部放弃 |
| 不做适配（强绑定 MySQL） | 可用 MySQL 全部能力（JSON 算子、`ON DUPLICATE KEY UPDATE`、全文检索等）；实现最省 | 换库等于重写数据层 |

**影响面**：决定 D-05、D-06、D-08，以及所有 SQL 能用的语法范围。
**事实**：数据库无关会把 SQL 限制在各方言交集——不能用 JSON 算子、`SKIP LOCKED`（SQL Server 无此语法，只有 `READPAST` 提示）、`MERGE`、`RETURNING`、各方言 upsert。
**状态**：待用户决定。

### D-08 数据库迁移工具

| 选项 | 优点 | 缺点 |
| --- | --- | --- |
| Flyway | SQL 优先、零魔法（与手写 SQL 取向一致）；支持的数据库面广 | **不翻译方言**，多库需按方言分目录、手工维护多份 DDL |
| Liquibase | changelog 抽象可覆盖可移植 DDL；`dbms` 属性让一个 changeset 跑在多库上 | 遇厂商特有类型（JSON、布尔、时区）与性能索引选项仍要写 `dbms` 标记的重复 changeset；多一层抽象需学习 |
| 不使用迁移工具 | 无额外依赖 | 无版本化、无回滚、无法审计 schema 变更 |

**影响面**：schema 演进流程、多库 DDL 维护成本。
**状态**：待用户决定。

### D-09 AI 接入层与智能体编排

| 选项 | 优点 | 缺点 |
| --- | --- | --- |
| Spring AI | 第一方、与 Boot 4.1 对齐；模型接入、embedding、17+ 向量库、RAG advisor、工具调用、MCP、可观测性齐备 | 智能体编排能力弱：无沙箱、无人工审批、无分布式会话状态 |
| LangChain4j | Boot 3/4 starter 数量最多；AI Service 抽象（声明式接口）体验好 | 同样是管道层，无企业级智能体运行时；与 Spring AI 功能高度重叠，二选一即可 |
| AgentScope Java | 智能体运行时能力最全：推理循环、子智能体、会话与会话恢复、沙箱执行、权限与人工审批引擎、分布式状态存储（Redis/MySQL/PG）、控制平面；Apache-2.0；有官方 Boot starter 且对齐 Boot 4.0.1；中文资料完善 | 2.0.0 GA 仅 3 个月（2026-07-10），仓库一年内 891 个未关 issue；RAG/embedding 未进入 v2 文档；可观测性仅 OTel 中间件，无 Prometheus；无独立第三方生产案例（案例均为阿里自述） |
| 自行封装模型客户端 | 依赖最少，完全可控 | 需自己处理流式、重试、工具调用协议、用量记账、多供应商差异 |

**影响面**：AI 相关全部实现方式；与「将来是否接入向量检索」相关。
**事实**：AgentScope 与 Spring AI **不在同一层且接口不互通**——AgentScope 有自己的 `ChatModelBase`，无法注入 Spring AI 的 `ChatModel`；但两者可在同一个 Boot 4 应用中共存（自动配置互不冲突）。
**状态**：**已裁决（2026-10-09）——只用 AgentScope Java，不叠加 Spring AI。** 理由与必须自行补齐的四项能力见 `.agent/rules/always.md` 的 D-09 条目。 模型供应商定为 **DeepSeek**（`deepseek-flash`），接入细节见 `.agent/references/agentscope-and-deepseek-2026-10.md`。

### D-10 认证方式

| 选项 | 优点 | 缺点 |
| --- | --- | --- |
| HTTP 会话 Cookie | Spring Security 默认配置即可；无需处理令牌刷新；浏览器端安全属性成熟（httpOnly + SameSite + CSRF） | **在桌面壳中不可靠**：桌面页面来源非 http(s) 域（Tauri 自定义协议、Electron `file://`），`SameSite`/`Secure` 语义失效，跨域请求撞 CORS |
| 自签 JWT | 无状态、易水平扩展；两端行为一致 | 撤销与续期需自行设计（黑名单或短时效 + 刷新令牌）；一旦签发无法即时失效 |
| OAuth2 / OIDC + PKCE | 标准协议；桌面端可用系统浏览器完成登录并深链回调，符合 IdP 政策；令牌存操作系统凭据存储 | 实现复杂度最高；需处理刷新令牌轮换竞态与深链单实例 |

**影响面**：后端 Spring Security 的配置形态（表单会话 vs 资源服务器），前后端会话状态机，桌面端登录流程。
**事实**：把 IdP 登录页嵌在 webview 中可能违反供应商政策（例如 Google 会阻止）；桌面端来源下 cookie 会静默丢失。
**状态**：待用户决定。

### D-11 前端框架与渲染模式

| 选项 | 优点 | 缺点 |
| --- | --- | --- |
| Vite + React Router（SPA） | 最简、最省；无服务端成本；与桌面壳天然兼容（静态产物直接加载） | 无 SSR，公开页 SEO 需另建 surface |
| React Router 框架模式（可切换 ssr） | 同一工程支持 `ssr:false` 的 SPA 与按路径预渲染，一个代码库兼顾应用与 SEO 页 | 框架模式约定更多；与桌面壳共享时仍需只取 SPA 产物 |
| Next.js | SEO 与流式渲染开箱即用；生态最大 | 主体应用是登录后 SPA，SSR 用不上；静态导出子集排除了 cookies/headers/middleware/server actions，桌面壳只能吃静态导出，等于维护两套构建配置 |
| TanStack Start | 类型安全的路由与数据加载 | 文档仍标 RC，稳定性未经大规模检验 |

**影响面**：前端工程结构、构建产物、部署形态、SEO 接入成本、桌面壳共享方式。
**状态**：待用户决定。

### D-12 桌面壳技术

| 选项 | 优点 | 缺点 |
| --- | --- | --- |
| Tauri 2.x | 复用系统 WebView2，不打包 Chromium，安装包与内存占用小；原生插件齐备（fs/sql/deep-link/updater/tray/store）；内置更新器 | 需要 Rust 工具链与 MSVC 构建环境；依赖系统 WebView2（老旧 Windows 需引导安装）；更新器签名密钥丢失后无法再更新既有用户 |
| Electron | 自带 Chromium，跨系统渲染完全一致；原生模块生态最成熟；团队熟悉度最高 | 安装包与内存占用显著更大；需自行声明 CSP |
| Wails | 与 Tauri 同模型（系统 WebView），后端用 Go | 团队若非 Go 技术栈则学习成本高 |
| Neutralinojs | 体积极小，无 Chromium | API 面最小；更新机制需自建 |
| PWA / 可安装 Web 应用 | 几乎零额外成本；Windows 可从 Edge 或应用商店安装；支持离线、推送 | **不是真正的 exe**：无法驱动系统托盘、控制原生窗口、读写注册表或常驻后台服务 |

**影响面**：交付形态、构建环境（是否需要 Rust）、CI 矩阵、更新与签名流程、可用的原生能力。
**状态**：待用户决定。

### D-13 前端数据层与状态管理

| 选项 | 优点 | 缺点 |
| --- | --- | --- |
| TanStack Query + Zustand | 服务端缓存与客户端状态职责清晰；生态成熟；体积小 | 两套心智模型 |
| RTK Query | 与 Redux 生态一体，团队若已熟悉 Redux 上手快 | 引入 Redux 体系，样板较多 |
| SWR + Context | 最轻 | 缓存与失效能力弱于 TanStack Query |
| 自行封装请求层 | 无额外依赖 | 缓存、去重、重试、失效都要自己写 |

**影响面**：前端代码组织方式、与流式响应的配合。
**状态**：待用户决定。

### D-14 消息与异步机制

| 选项 | 优点 | 缺点 |
| --- | --- | --- |
| 仅进程内事件 | 零额外基础设施；实现与调试简单 | 无跨进程投递保障；服务拆分时需要改造 |
| 进程内事件 + outbox 表 | 事件与业务同事务写入，重启可重投，不丢事件；为零改造外置到消息中间件留好接缝 | 需维护投递状态表与重投逻辑 |
| 引入 Kafka / RabbitMQ | 跨服务解耦、削峰、可重放 | 运维中间件；需处理幂等、乱序、毒消息与死信；事件 schema 会变成隐性共享契约 |

**影响面**：跨模块通信方式、可演化性、运维复杂度。
**状态**：待用户决定。

### D-15 缓存与其他基础设施

| 决策点 | 选项与权衡 |
| --- | --- |
| 缓存 | 无缓存（最简单）／ Caffeine 本地缓存（无网络开销，多实例间不一致）／ Redis（一致、可共享，需运维） |
| 对象存储 | 本地磁盘（最简，难水平扩展）／ MinIO（自托管对象存储，需运维）／ 云对象存储（免运维，有成本与厂商绑定） |
| 可观测性 | Actuator + Micrometer + OpenTelemetry（开源、可移植）／ 仅结构化日志（最省）／ 商用 APM（功能强、有成本） |
| 国际化 | 不需要／ 需要并采用前后端资源文件方案（需明确支持的语言与区域处理规则） |
| 测试栈 | 后端：JUnit + Testcontainers（真实数据库，慢但可信）／ 内存库（快但不验证方言，与多库目标冲突）；前端：Vitest（组件）+ Playwright（端到端，且可用于 Web 与桌面壳） |

**状态**：待用户决定。

## C. 选项之间的锁定关系（事实描述）

以下是选项之间的**客观约束**，用于判断决策顺序，不构成建议：

1. **D-01 决定 D-02、D-04**：是否服务化决定模块边界的强制手段与仓库结构。
2. **D-01 决定 D-14 的必要性**：单体形态下进程内事件 + outbox 即可满足；跨服务才需要消息中间件。
3. **D-07 反向决定 D-05、D-06、D-08**：多库适配深度越深，主键、分页、迁移三处越不能依赖单一数据库特性；反之若强绑定 MySQL，这三处可用最省方案。
4. **D-12 反向约束 D-10、D-11**：选择桌面壳后，cookie 认证的可行性被否定，前端也不能是纯 SSR 形态。
5. **D-09 内的分层关系**：Spring AI / LangChain4j 与 AgentScope 处于不同层且接口不互通，可共存；选择 Spring AI 不排除将来引入 AgentScope，反之亦然。
6. **D-11 与 SEO 需求绑定**：是否需要公开页 SEO 直接决定 D-11 的可行集合。
